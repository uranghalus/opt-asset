# Classification chain codes are immutable once referenced

`kode_asset` is generated by concatenating the classification chain codes (golongan → kategori → kelompok → sub kelompok) plus a per-tenant sequence, so changing a code silently invalidates every previously generated asset code built from it (grill 2026-09-29). Decision: a chain code is editable only until a child level, item, or asset references it; once referenced it is locked, enforced by DB foreign keys plus a policy check on update.

## Considered options

- **Fully immutable from creation** — simplest to reason about, but freezes typos in top-level codes behind data migrations.
- **Freely editable** — maximum flexibility, but previously generated `kode_asset` values become unverifiable against their chain, undermining the audit intent of rules §1.3.
- **Immutable once referenced (chosen)** — typos fixable while safe; history stable after first use.

## Consequences

- T03 must implement the referenced-check on code updates (child level, item, or asset exists → reject) alongside the DB FKs that make re-parenting/re-coding of referenced rows impossible at the storage level.
- Renaming an entire chain branch later is a deliberate data-migration exercise, never a UI edit.
